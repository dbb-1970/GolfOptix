# Crew — November 10, 2026

## Available workflow

Crew follows Maintenance on the course overview and phone navigation. The authenticated route is `/crew/?course=kings-ridge-kings`; the separate public showcase is `/test-drive/crew/`. Navigation remains available back to Maintenance, the permitted course map, the account and home. Crew-only users are routed directly to Crew by sign-in and are not given course-map or maintenance-calendar permissions.

Superintendents/administrators can add private worker profiles (name, email, job title and optional DOB), assign dated work/shifts with location/instructions, review and print tickets, mark assignments completed/cancelled, archive/restore workers, and copy one individual's week or month to a destination period. Copying creates new Scheduled assignments and tickets, never overwrites old work, reports missing month dates and atomically refuses overlaps, including overnight work. Calendar views are Month, Week and Day; selecting a month date opens that day. Times are planned course-local wall-clock times in America/New_York, not payroll/time-clock records.

The user confirmed ordinary crew see **only their own schedule and tickets**. The later closure workflow permits them to log work and submit draft closure on their own assigned tickets; all other schedule/personnel edits remain manager-only. DOB, contact roster, other workers, notification records and manager history are omitted from their API response. The exact normalized title Assistant Superintendent, saved by a manager, permits Crew management. Existing administrative and superintendent permissions remain intact. Editing a self-service profile title does not grant access. An Assistant Superintendent cannot change their own delegated personnel profile/access. Archiving a worker immediately stops Crew API access while retaining their history.

This does not turn ordinary crew into full course members. The previous Kings full-map membership restriction stays intact. A separate `crew` Identity role allows the Crew shell; the server additionally requires a bound, active worker identity in the requested course. Assistant Superintendents manage the Crew area; this release does not grant them the Kings map or maintenance calendar automatically.

## Storage and authentication

Private personnel/schedules/notification records use a strongly consistent Netlify Blob store `golfoptix-crew-v1`, partitioned by course. Writes require authenticated manager authorization, same-origin requests, a matching revision, record versions and ETag compare-and-set. Persistence is read back before success is reported. Stable record IDs and authenticated actor/time audit records are retained. No equipment inventory is created by Crew or by catalog browsing.

Crew profiles are not public catalog entries. DOB is not written to Identity user metadata, welcome emails, work-ticket messages, public files or crew-reader projections. The Privacy Policy describes these practices and the transactional email processor.

## Welcome and assignment emails

The owner explicitly authorized mail.golfoptix.com verification, a domain-restricted sending-only Resend key, and storage in GolfOptix's private Netlify settings. Three records were added to the existing Netlify DNS zone: TXT `resend._domainkey.mail`, CNAME `rsend.mail`, CNAME `send.mail`, all TTL 300. The seven pre-existing website/Google mail records were retained. Resend shows the domain **Verified**.

`RESEND_API_KEY` is a Netlify secret with a value only in the Production deploy context. The free Netlify plan fixes its allowed scopes to Builds, Functions and Runtime; post-processing is excluded for secrets. No value is supplied to previews, branch deployments, local development or agent runners. The key is restricted within Resend to Sending access for mail.golfoptix.com. It was transferred through the browser directly to Netlify, never written to source, local configuration or logs, and the temporary clipboard copy was cleared. `CREW_EMAIL_FROM` is `GolfOptix Crew <crew@mail.golfoptix.com>`.

Creating a worker queues a welcome. The scheduled email worker runs every five minutes on production, processes a bounded batch under a time budget and uses per-job leases plus provider idempotency keys. It cannot be invoked as a public scheduled-function URL. Work assigned or changed in **Crew** creates a ticket and queues a notification to that worker. Existing Maintenance calendar free-text assignments remain a separate workflow and do not automatically generate Crew tickets in this release.

New identities get a random temporary password through the managed Identity administration API. It is included in the welcome email, retained only in function memory while sending, and never stored plaintext in crew data or responses. Crew records remain inaccessible until the user changes that password, and temporary access expires after 72 hours. Existing users keep their chosen passwords and existing roles. A replacement welcome only resets a still-temporary credential. It never resets an established password. A linked identity's email must match the saved worker recipient before a ticket is sent.

A welcome with uncertain delivery is held for explicit reissue, rather than silently generating another password and invalidating a possibly delivered message. Status is **Accepted by email service**, not proof of inbox delivery. Unconfigured sending leaves jobs pending and creates no identity/credential. The manager can use **Email & login status → Send me a test email** to test their own signed-in address; the endpoint does not accept arbitrary recipients and uses provider idempotency to limit duplicate test sends. A test creates no personnel record, assignment or credential.

Resend's free plan at review: 3,000 messages/month and 100/day. No paid plan or overage option was enabled. Quota/provider failures remain visible as unconfirmed delivery and require review. This release does not include inbound email, delivery webhooks, bounce handling or automatic conversion of existing browser-local map repairs into shared work orders. The later work-order release adds an explicit Share work order online action for those legacy repairs.

Sources: [Resend pricing](https://resend.com/pricing), [Resend idempotency](https://resend.com/changelog/idempotency-keys), [Netlify scheduled functions](https://docs.netlify.com/build/functions/scheduled-functions/), and the installed @netlify/identity 2.0.0 type/API definitions.

## Course-specific welcome setup

Welcome emails now link to `/login/?setup=crew&course=<club-id>&track=<track-id>`. Both dropdowns are populated from the real catalog using the inviting superintendent’s track, with an explicit account-setup heading and temporary-password instructions. This signs into the already-provisioned crew identity rather than attempting a duplicate signup. After authenticated course-access confirmation, it opens that track’s Crew portal and its required password-change screen for new temporary accounts. Existing users retain their chosen passwords. Course hints never grant membership; mismatched, unavailable and demo-track Crew invitations are rejected. No credential or recipient email is placed in the URL.

Ordinary `/login/?signup=1&course=<club-id>&track=<track-id>` links also open Create account with the requested course and track selected; public signup still requires verification and administrator approval. The setup-test email previews the new course-specific setup URL. Previously delivered emails cannot be rewritten. Browser checks confirm both forms’ preselection; tests cover generated welcome content, invalid track hints and authenticated post-login routing. The recipient confirmed the approved setup test arrived in Junk. No additional email or real worker was created for this update. Rollback for this follow-up: `0c103b1b17ab06126ead4f7cd1dfa7c3a1156a6b`.
